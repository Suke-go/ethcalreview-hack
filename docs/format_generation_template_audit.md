# 公式様式に基づく生成テンプレート精査

## 結論

`docs/Format` に追加された公式様式を生成テンプレートの基準にする。現行の `backend/templates` は、ほぼプレースホルダ化されておらず、旧研究の課題名・実験内容・担当者名・連絡先が残っている。特に同意書と同意撤回書は現行オーケストレータでテンプレートをコピーしているだけなので、旧研究情報がそのまま出力される。

実装方針は、単純な `{{ placeholder }}` 置換ではなく、文書ごとに項目単位で上書きするテンプレート仕様を持つ形にする。公式 docx は Word のフォーム部品やコンテンツコントロールを持たず、通常段落と表だけで構成されているため、`docxtpl` または `python-docx` による段落・表セル単位の差し替えで十分に扱える。

重要な前提として、旧値は単なる削除対象ではなく、責任者・提出先・予算・部屋・連絡先のプリセット候補として扱う。ただし、旧研究の課題名、実験内容、参加者データは出力に混入させない。

## プリセット設計

責任者、提出先、系、予算、部屋、TEL は研究ごとに毎回自由入力させるのではなく、選択すると関連項目が自動決定されるようにする。特に善甫啓一を実施責任者にするケースは既定値候補として扱う。

プリセットは後から変更できるアーキテクチャにする。コードに固定値として埋め込まず、設定 JSON または管理画面から追加・編集・無効化できるデータとして扱う。初期値は同梱してよいが、運用中に提出先、責任者、域長、予算、部屋、TEL が変わっても、アプリ本体のコード変更なしで更新できることを前提にする。

推奨する保持方法:

- `backend/presets/*.json` または `settings.json` 配下にプリセットを保存する。
- 初回起動時は同梱デフォルトを読み込み、ユーザー編集後はユーザーデータ領域の設定を優先する。
- 各プリセットには `id`、`label`、`version`、`enabled`、`updated_at` を持たせる。
- UI ではプリセット選択、複製、編集、新規追加、無効化をできるようにする。
- 生成済みセッションには、生成時に使ったプリセット値のスナップショットを保存する。後でプリセットを変更しても、過去の出力履歴や再レビューが別値にすり替わらないようにする。
- 公式様式そのものが変更された場合に備え、プリセットとテンプレートのバージョンを別々に管理する。

### 責任者プリセット

`principal_investigator_presets` のような配列を持ち、責任者選択時に以下をまとめて埋める。

| フィールド | 例 |
| --- | --- |
| `id` | `zempo_keiichi` |
| `name` | 善甫 啓一 |
| `affiliation` | 筑波大学システム情報系 |
| `domain` | 知能機能工学域など |
| `position` | 准教授 |
| `email` | `zempo@iit.tsukuba.ac.jp` |
| `tel` | `029-853-5338` |
| `default_rooms` | `3M211`, `3G214` など |
| `default_budget_accounts` | よく使う予算候補 |
| `default_ethics_office_id` | 提出先プリセットへの参照 |
| `default_domain_head_id` | 関係組織の長プリセットへの参照 |

注意点:

- 責任者を選んだ時点で、申請者欄、実施責任者欄、問い合わせ先、同意書・撤回書の責任者欄に同じ値を流す。
- 実験実施分担者は責任者とは別に入力・選択できるようにする。
- 旧値に出てくる部屋番号や予算名は、責任者プリセットの候補として取り込み、研究ごとに上書き可能にする。

### 提出先・系プリセット

システム情報系と図書館情報メディア系では、宛名、倫理委員会名、事務局、TEL、関係組織の長が変わり得る。提出先を選択すると以下を自動決定する。

| フィールド | 内容 |
| --- | --- |
| `submission_destination_id` | `systems_information` / `library_information_media` など |
| `recipient` | `システム情報系長　殿` など |
| `committee_name` | 系の研究倫理委員会名 |
| `office_name` | エリア支援室・事務局名 |
| `office_tel` | 事務局 TEL |
| `default_affiliation_label` | 申請書や同意書で使う所属表記 |
| `domain_head_candidates[]` | 域長・系長などの候補 |
| `template_variant` | 提出先ごとに文言差がある場合のテンプレート差分 |

UI 方針:

- 研究者は「提出先/系」を先に選ぶ。
- 提出先を選ぶと、宛名、倫理委員会事務局、TEL、関係組織の長候補が自動で入る。
- 責任者を選ぶと、所属、職名、氏名、メール、TEL、よく使う部屋、予算候補が自動で入る。
- 自動入力された値は固定ではなく、今回の申請に限って手動修正できる。

## フォーマット維持のガードレール

このシステムでは、公式 docx の体裁を大きく変えた不十分な docx を生成しないことを最優先にする。LLM や `python-docx` でゼロから似た文書を作る方式は、公式様式の余白、段落、表、チェック欄、宛名、署名欄を崩しやすいため、申請書・同意書・同意撤回書では避ける。

必須ルール:

- 公式 docx をベースにして、既存の段落・表・ページ構成を維持する。
- 公式様式の見出し、署名欄、日付欄、受付日・承認日欄を削除しない。
- 余白、ページサイズ、表セル、段落順、固定文を原則変更しない。
- 自由記述が長い場合も、項目位置を維持して本文だけを差し替える。
- **公式様式に追随する**。様式の番号体系は大学が配布する最新版に合わせる（独自に作り替えない）。2026/04/22 改訂で公式様式が `1.x / 2.x / 3.x …` 構成（`01-1_研究倫理審査申請書_260422.docx`）になったため、これを正本とする。旧 `１〜１４` 番号体系は退役。
- LLM に docx レイアウトを任せない。LLM は本文候補の生成に限定し、レンダリングは決定的なテンプレート処理で行う。
- 生成後に Word 文書内の全テキストを抽出し、旧値・未置換プレースホルダ・必須欄空欄を検査する。

「実施計画書」は自由様式のためゼロから生成してよいが、それでも申請書・同意書と整合する章立てと本文を使い、不必要に派手な体裁や別様式風の装飾は入れない。

### `実験参加者リスト.xlsx`

参加者名簿テンプレートである。`公式` シートは空欄中心だが、`Sheet1` に実名・メールアドレスのサンプルデータが含まれている。生成物にそのままコピーしてはいけない。

対応方針:

- テンプレートとして使う場合は `Sheet1` を削除または空欄化する。
- 入力された参加者データがない場合は空の `公式` シートのみ出力する。
- 入力された参加者データがある場合だけ、No.、氏名、所属、メール、住所、実験日、謝礼形式、金額を埋める。

## 推奨するテンプレート方式

### 1. 公式様式を正本としてテンプレート化する

`backend/templates` の既存 docx をそのまま温存するのではなく、`docs/Format` の公式ファイルをコピーしてサニタイズしたものを正本にする。

推奨ファイル:

| 出力種別 | 正本テンプレート |
| --- | --- |
| 研究倫理審査申請書 | `backend/templates/01-1_研究倫理審査申請書_template.docx` |
| 同意書 | `backend/templates/03_同意書_template.docx` |
| 同意撤回書 | `backend/templates/04_同意撤回書_template.docx` |
| 謝金根拠 | `backend/templates/謝金単価の根拠_template.docx` |
| 参加者リスト | `backend/templates/実験参加者リスト_template.xlsx` |

### 2. 項目単位のレンダラを持つ

単純な全文置換ではなく、文書ごとに以下のようなレンダラを持つ。

- `render_application_form(context)`
- `render_consent_form(context)`
- `render_consent_withdrawal(context)`
- `render_honorarium_rationale(context)`
- `render_participant_list(context)`

各レンダラは、見出しや固定文を残し、値段落・表セル・チェックボックス文字だけを更新する。

### 3. 共通コンテキストを正規化する

生成前に camelCase と snake_case を混在させず、以下の正規化済み構造へ寄せる。

| フィールド | 内容 |
| --- | --- |
| `research.title` | 課題名 |
| `research.background` | 背景 |
| `research.purpose` | 目的 |
| `research.significance` | 意義 |
| `research.method` | 方法 |
| `research.period.start_text` | 研究開始日、通常は承認後 |
| `research.period.end_date` | 研究終了日 |
| `applicant` | 申請者、実施責任者または指導教員 |
| `principal_investigator` | 実施責任者 |
| `conductors[]` | 実験実施担当者、実施分担者 |
| `collaborators[]` | 申請書の実施分担者 |
| `domain_head` | 関係組織の長 |
| `facilities` | 実施施設 |
| `funding` | 費用の出所 |
| `reward` | 謝金有無、形式、単価、時間、人数、総額、根拠 |
| `participants` | 条件、人数、選択基準、除外基準、募集方法 |
| `procedures[]` | 実験手順 |
| `risks[]` | 想定リスク |
| `risk_countermeasures[]` | リスク対策 |
| `recording` | 動画・音声・画像記録の有無と公開有無 |
| `data` | 取得データ、匿名化、対応表、管理、保存、処分、開示 |
| `consent` | 対象者年齢、本人意思確認、説明方法、撤回期限 |

| `attachments` | 添付書類チェック |
| `ethics_office` | 委員会事務局名、電話 |

## 実施計画書の自由様式テンプレート

実施計画書は自由様式だが、申請書・同意書との整合性を保つため、以下の章立てを固定する。

1. 課題名
2. 申請研究の概要
3. 背景
4. 目的
5. 意義
6. 実験方法
7. 実験参加者
8. 募集方法
9. 同意取得方法
10. 実施場所・研究期間
11. 実験装置・使用機器
12. 実験手順
13. 所要時間
14. 想定される精神的・身体的負担
15. 安全対策・中止基準・緊急時対応
16. 個人情報・研究データの取り扱い
17. 同意撤回とデータ破棄
18. 謝金
19. 研究成果の公開

生成時の制約:

- 申請書 9、10、11、12 と同じデータ管理・撤回・公開方針を使う。
- 同意書の参加条件、方法、所要時間、リスク、謝礼と矛盾させない。
- 「可能性がある」「考えられる」だけで終わらせず、各リスクには対応策を付ける。
- 未入力情報を断定しない。必須情報が足りない場合は質問対象に回す。

## 検証条件

テンプレート生成後に以下を自動検証する。

1. 出力 docx/xlsx に旧課題名が残っていない。
2. 出力 docx/xlsx に旧担当者名、旧メールアドレス、旧部屋番号が残っていない。
3. `{{ ... }}`、`{% ... %}`、`temp`、`affliation`、`name` が残っていない。
4. 申請書、同意書、撤回書の課題名が一致している。
5. 同意撤回期限が申請書、同意書、実施計画書で一致している。
6. 謝金額、謝金形式、所要時間が申請書、同意書、実施計画書、謝金根拠で一致している。
7. 動画・音声・画像記録なしの場合、同意書に `ビデオ録画を含めた` が残っていない。
8. 参加者リストのサンプル個人情報が出力に含まれていない。

## 実装優先順位
